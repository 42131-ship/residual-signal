## 1. 这个决策在哪一步会崩

**视觉调优阶段**：当美术要求"节点 7 的入口灯光再往左 8px"或"这个走廊感觉太窄，能试试加宽 16px 吗"时，你需要：
1. 手改 nodes.json 里的坐标/尺寸
2. 重跑代码生成
3. 启动游戏验证
4. 不满意再循环

编辑器的价值是**所见即所得的迭代**。没有它，每次微调都走完整构建链，反馈周期从秒级退化到分钟级。

**多人协作时**：策划想调节点布局，美术想调灯光遮罩，程序要改碰撞体。三人同时改 nodes.json 会产生合并冲突，但这个 JSON 既是数据又是"源码"，冲突时无法靠 git diff 判断谁的意图正确。

## 2. 我漏掉了什么成本

**人肉编辑器税**：nodes.json 现在是 16 节点，三个月后可能 60+ 节点 × 每个 8 字段。手写 JSON 的心智负担会线性膨胀，错误率也会（少一个逗号、拼错枚举值、坐标打错正负号）。

**调试可见性**：编辑器给你层级面板、网格对齐、碰撞体预览。纯代码流意味着你要在脑内模拟坐标系，或写一堆临时 debug 渲染代码来"看见"拓扑。

**onboarding 成本**：新成员加入时，编辑器 10 分钟上手；读 nodes.json schema + 代码生成逻辑需要 2 小时 + 一个下午的答疑。

## 3. 如果三个月后必须回退到 A 或 B，代价是什么

**需要改动**：
- 新增 `tools/import_ldtk.py`（或 tiled_tmx）约 400 行（解析层级、实体、自定义属性映射到 nodes.json）
- `data/` 下新增编辑器工程文件（.ldtk 或 .tmx）
- 修改 CI 门禁：先跑导入器，再跑现有校验
- 迁移现有 16 节点：手工在编辑器里摆一遍（2–4 小时），或写一次性脚本从 nodes.json 反向生成编辑器格式（6 小时）

**工作量**：以 16 节点 / 5 模板为基数，导入器 + 迁移脚本约 **2 人日**，手工迁移 + 工作流文档更新约 **1 人日**。但真正的成本是**切换期的双轨维护**：在所有人都迁移到编辑器前，nodes.json 仍需手动同步。

## 4. 一句话判决

**C 成立但需附加条件 X**：必须在三周内实现一个极简的 nodes.json 可视化工具（只读预览 + 坐标网格叠加层），否则视觉迭代税会在一个月内迫使团队回退到编辑器。
